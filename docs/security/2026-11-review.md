# Pre-launch security review

Last updated: 2026-10-30

This is the record of the security review done before the public launch of Habitués. It says what was checked, what was found, what was fixed, and what the owner must still do on the hosted project.

## Scope and method

Five areas were reviewed, each by an independent reviewer who worked read-only on the branch `feat/security-launch`:

1. Database: row-level security, grants, security definer functions, write limits, views.
2. Sign-in and sessions: Supabase Auth settings against spec section 18.5, admin second factor, bans, session storage, web sign-in flow.
3. Web: HTML and JSON-LD escaping, headers and CSP, redirects, cache behaviour, sitemap cost.
4. Edge Functions: `send-push`, `storage-cleanup`, `submit-feedback`.
5. App and supply chain: secrets in the bundle, Android permissions, deep links, uploads, dependencies, CI.

Every finding had to come with a concrete exploit path: who the attacker is, the exact request or steps, and what they gain. A finding without one was marked "to verify" and never rated high. The implementer then re-checked each finding, assigned the final severity, and fixed it with a test where the problem could be tested.

Severity scale:

- **high:** another person's private data or account is reachable, privilege escalation, authentication bypass, or stored script injection on the public site.
- **medium:** a realistic abuse with limited impact (enumeration, getting past a spam limit, a missing header on a route, a leak of non-sensitive data, a denial of service cheaper than the defences allow).
- **low:** hardening and defence in depth.

Already known and accepted before the review, and not re-reported: the search and importer helper functions without a fixed `search_path` (kept inlinable on purpose, security invoker), `zod` via `@expo/cli` in `npm audit` (build time only), and the hosted dashboard settings that the repository cannot show.

## Accepted risks

- **DB-8, token takeover.** Handing a known push token to the caller is the normal case of a shared or resold device. Tokens cannot be read through the API, so an attacker needs a leaked token. The format and count limits from FN-1 apply.
- **AUTH-4, banned person's read access.** A banned person's token still reads data until it expires. JWT expiry is set to 3600 seconds or less, writes are refused immediately, and a ban releases their club claims.
- **AUTH-6, no Google nonce.** The Android sign-in library offers no nonce in its free edition. A stolen ID token could be replayed until it expires, but Google issues one only for this app's registered package and signing key.
- **AUTH-7, Turnstile only on the code request.** Supabase does not check CAPTCHA on Google sign-in or code verification. Google limits its own sign-ups, and verification is bounded by the per-IP limit and the 8-digit, 10-minute code.
- **AUTH-8, session in localStorage on the web.** Decision: accepted, not hardened. The static `/app` shell has no server part that could hold the refresh token in an HttpOnly cookie, so browser storage is the only option. The control is that script injection is hard on `/app`: the CSP is `script-src 'self' https://challenges.cloudflare.com` with no inline scripts and no other third-party scripts, and the app renders no user-supplied HTML. Signing out clears the `sb-*` keys. On the phone the session stays in encrypted storage. The privacy text should say that on the website the session is kept in the browser's storage.
- **APP-5, EXIF removal only on the phone.** Decision: accepted. Server-side image processing would need an image library in an Edge Function or a Storage webhook, which is not affordable on the free tier. Mitigation in place: the app re-encodes avatars and feedback screenshots and removes metadata before upload; the server enforces type and size (1 MB, JPEG) and gives avatars a random name. The only person exposed by bypassing the app is the uploader. The spec sentence "uploads checked server-side: file type, size, EXIF removal" was corrected to say what really happens. Claim documents are uploaded unchanged and are private.
- **WEB-6, takedown delay.** A removed page can be served for 5 minutes from the edge cache and 1 minute from a browser. For an urgent takedown, purge the URL in Cloudflare.
- **FN-5, service key as shared secret.** The comparison is now constant-time. Replacing the key with a dedicated cron secret needs a Vault rotation and two cron migrations, and was not done.
- **FN-6, `net` grants.** Migrations run as `postgres`, which cannot revoke grants made by `supabase_admin`. The schema is unreachable while the API exposes only `public` and `graphql_public` (tested).
- **FN-2, per-instance limit.** The anonymous feedback limit (10 per client and hour, 200 per hour overall) is held in memory per function instance, so it is a brake and not an exact limit.

## Known limitations

- **Lifting a ban does not restore a person's activities.** Banning a person removes or releases what they organised (and, since DB-4, their club claims). Unbanning restores their access but not that content. This was known and accepted before the review.
- **Column grants on `activities` and `collectifs`** do not cover columns added later. A new column needs an explicit grant or the app cannot read it.
- **Existing profile photos were dropped** by the avatar migration (test accounts only before launch).
- **Unbounded fresh page ids** on the public site still reach the database. Only the Cloudflare rate-limit rule bounds them.
- **Auth rate limits per IP.** The limits (10 verifications and 15 sign-ins per 5 minutes per IP) are tight for people behind a shared mobile-carrier address. Watch for 429 responses at launch.
- **Post-deploy checks live in two places.** The WEB-8 check is in the README and in `docs/launch/checklist.md` (step 6), which also carries the other owner actions in order.

## Owner actions on the hosted project

These settings cannot be carried by the repository. Details and exact values are in `README.md`.

Supabase, Authentication:

1. Confirm email: ON. Secure password change: ON. Secure email change: ON.
2. Email OTP length 8, expiry 600 seconds.
3. Both the Magic Link and the Confirm signup templates carry `Votre code Habitués : {{ .Token }}` and no link.
4. Rate limits: token verifications 10 per 5 minutes per IP, sign-ups and sign-ins 15, token refreshes 100. Set the e-mail rate limit to what the SMTP provider allows. Custom SMTP is strongly recommended.
5. Allow new users to sign up: ON. Anonymous sign-ins: OFF. Manual linking: OFF. Phone sign-up and phone MFA: OFF. Only the Google provider is on, with Skip nonce check ON.
6. JWT expiry 3600 seconds or less. Refresh-token rotation ON, reuse interval 10 seconds.
7. CAPTCHA (Attack Protection): Turnstile with its secret key. After deploying, call `POST <SUPABASE_URL>/auth/v1/otp` with the anon key and no `captcha_token`, and expect a `captcha` error (WEB-8).
8. MFA TOTP enrolment and verification ON. Promote the first admin with their phone at hand and check `auth.mfa_factors` straight afterwards (AUTH-9).
9. Redirect URLs: exact addresses only, no wildcard. Add a preview address only for a test and remove it afterwards.
10. API, exposed schemas: only `public` and `graphql_public` (FN-6).
11. Run `supabase db push` so that migrations up to 049 are applied (the password-blanking trigger is a migration).

Supabase, Edge Functions and Vault:

12. `TURNSTILE_SECRET`, `ALLOWED_ORIGINS=https://<site>` and `TURNSTILE_HOSTNAMES=<site host>,challenges.cloudflare.com` for `submit-feedback`.
13. The Vault secrets used by the `send-push` and `storage-cleanup` cron jobs, and both functions deployed, so that files queued for deletion (including replaced avatars) are removed.

Cloudflare:

14. Rate-limiting rule: 60 requests per 10 seconds per IP on `/activites/*`, `/associations/*`, `/sitemaps/*` and `/app/*`, block for 10 minutes (WEB-1).
15. Pages Functions failure mode: Fail open. Use a custom domain, because the Cache API does nothing on `*.pages.dev`.
16. WAF managed rules ON, SSL Always Use HTTPS, DNSSEC with the DS record at the registrar.
17. Access policy on Pages preview deployments, and `WEB_BASE_URL` set for the Preview environment too (WEB-7).
18. For an urgent takedown, purge the URL in Cloudflare (WEB-6).

Google and GitHub:

19. Google OAuth: Web client id and secret in Supabase, and an Android client with the signing key's SHA-1.
20. GitHub: enable Dependabot alerts, secret scanning with push protection, and CodeQL as described in `SECURITY.md` and the repository settings guide. Dependabot keeps the pinned action SHAs up to date.
